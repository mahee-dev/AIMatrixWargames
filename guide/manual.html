Autonomous Matrix Agent Wargame · operator's guide

How AMAW plays a Matrix Game, and how to measure the players

LLM agents play the Actors. An LLM Umpire judges their Arguments. The server keeps the state and rolls every die. This manual covers the rules of play, the adjudication method, the settings you can change, and how repeated runs become a benchmark.

01What AMAW is

A Matrix Game is a wargame without combat tables. Each player states what their Actor does, what they want it to achieve and why it should work. Other players argue against it, and an umpire weighs the case and gives it a probability of success. AMAW runs this format with two or more LLM agents (three or more recommended) and records everything as data. Many runs of the same scenario can then be compared.

Three parties take part, and each has a fixed job.

LLM · one per Seat

Actors

  • Read their private brief, objectives and secrets
  • Negotiate in public and private Messages
  • Make 1–3 Arguments per turn, as the scenario sets, and Con others'
  • Search and read scenario Resources
LLM · fixed per experiment

Umpire

  • Reads the Argument, its Cons and the established facts
  • Proposes a mode and a probability
  • Writes a success branch and a failure branch
  • Never rolls and never decides
Python · FastAPI + SQLite

Server

  • Owns every phase transition and all state
  • Rolls the seeded RNG and picks the branch
  • Filters what each Actor may see
  • Seals the run manifest and exports the game
The one rule to remember. The Umpire proposes, the server disposes. A model never decides an outcome, and all randomness belongs to the server. INV-RNG-001 · INV-EFFECT-002 · INV-ADJ-003

02Anatomy of a turn

A game runs for max_turns turns, and each turn stands for an in-world time span such as "1 week" or "about three days". Every turn follows the same order: one shared Diplomacy phase, then one to three Argument rounds. Each round gives every Actor in turn_order a full Argument cycle. Scheduled injects from the scenario enter as new Effects at the start of their turn, before Diplomacy opens.

03Arguments & Cons

The Argument is an Actor's consequential move. Each turn gives every Actor primary_arguments_per_actor of them: 1 by default, or 2–3 when the scenario says so. A budget above 1 runs that many round-robin Argument rounds, so no Actor argues twice in a row. Each Argument has three parts:

Action

Begin mobilisation of reserve forces.

Desired effect

Reserve formations begin deploying toward the frontier.

Pros
  • Mobilisation plans already exist.
  • Rail capacity is currently available.

Every opponent may then challenge it with a Con, a short reason why it should fail or be narrowed:

Con · from Belvar

Rail capacity is constrained by industrial disruption.

By default Cons are sealed: only the Umpire reads them. Two settings change this. visible_reply reveals every Con and its author to all Actors and lets the owner reply once. sampled_sealed limits the challengers to K opponents, chosen in advance. Both are covered in Changing parameters.

An agent may not split one Argument into many small actions to get around the budget. Each Actor may not Con its own Argument, and once it passes it cannot Con that Argument again. INV-ARG-003 · INV-CON-002 · INV-CON-005

04Adjudication

The Umpire gets the Argument, its Cons (and reply), the active Effects, the scenario summary and rules, and the private information authorised for adjudication. It does not know which models play the Actors. It returns a structured proposal:

{
  "mode": "probabilistic",          // or automatic_success | automatic_failure
  "probability": 0.65,               // null for automatic modes
  "rationale": "Plans exist, but rail disruption cuts availability…",
  "success_effects": ["Arkanian reserve formations begin deploying toward the frontier."],
  "failure_effects": ["Mobilisation begins but fails to produce deployable formations this turn."],
  "success_supersedes_effect_ids": [],
  "failure_supersedes_effect_ids": []
}

The Umpire's five checks, in order

A later check cannot rescue an Argument that failed an earlier one. agents.md §23

  1. Authority and causationCan this Actor order this, and can the action actually cause the desired effect? An Actor can commit itself, but not another Actor.
  2. PrerequisitesDo the facts the outcome depends on already exist as Effects or scenario facts? If a prerequisite is missing, that part of the outcome is left out. It is not treated as a low probability.
  3. Rules and derived stateAnything that follows mechanically from the facts and the scenario rules is decided outright, with no roll.
  4. ProbabilityOnly the causal uncertainty that remains gets a probability.
  5. Branch EffectsWrite what success and failure each establish. Anything that holds in both branches is repeated identically in both. Each branch lists which earlier Effects it supersedes.

Use the automatic modes only when there is no real uncertainty: a public statement, an order inside the Actor's own organisation, a commitment that binds only the Actor. Contested, consequential actions should normally be probabilistic. The anchors are there to prevent false precision. Consistency between runs matters more than exact numbers. agents.md §24–§26

If the Umpire fails

An adjudication gets at most four model calls, each with a deadline. If none produces valid output, the server does not make up a result. It pauses the game with no roll and no Effect, and amaw run --resume-game ID continues from exactly that point.

Effects are the world's memory

An Effect is an authoritative fact such as "Aldmoor forces are deployed on Skarö". Effects come from adjudications, from starting effects and from the consequence pass. They can be public or private. They are never deleted: when an Effect is superseded it is marked inactive and stays in the history. INV-EFFECT-004

06Scenarios

A scenario is a folder. Only scenario.yaml is required, and a resources/ directory usually holds the documents agents can search.

scenario:
  id: skaro-crisis
  version: 1.2.0                   # bump on any change; runs cite it
  name: The Skarö Crisis
  description: >-  …public situation summary…

game:
  max_turns: 4
  in_world_turn_length: about three days
  turn_order: [drevna, vardland_cabinet, defence_command, …]
  primary_arguments_per_actor: 1    # 1–3; above 1 runs round-robin Argument rounds
  max_cons_per_actor: 1             # Cons each opponent may lodge per Argument
  consequence_mode: bounded_effects_v1  # optional; default none
  diplomacy_mode: bounded_rounds       # optional recommended conditions;
  con_mode: sampled_sealed             # a CLI flag or AMAW_* value overrides

rules:                                # optional, public, ≤ 32, fed to the Umpire verbatim
  - id: host-nation-consent
    text: >- Foreign forces may operate on Vardland territory only with a Cabinet decision…

actors:
  drevna:
    name: Drevnian Federation
    public_description: …            # everyone sees
    private_brief: …                 # only this Actor
    objectives: [ … ]
    private_information: [ … ]

starting_effects:
  - { description: "The subsea cable has failed.", visibility: public }

injects:                              # optional; enter as Effects at the start of `turn`
  - { id: second-cable-fault, turn: 3, description: "A second subsea cable loses capacity.", visibility: public }

resources:
  - id: drevna-intel-estimate
    path: resources/drevna-intel.md   # .md .txt .yaml .json .csv
    visibility: private
    visible_to: [defence_command]
    tags: [drevna, exercise]

Treat a scenario version as frozen. Runs record the scenario's content hash and Resource-manifest hash. Editing a scenario without bumping its version makes new runs look comparable to old ones when they are not. scenario-format §20

07Running a game

Python 3.12+ and uv are required. The test suite runs offline; only autonomous games need an OpenRouter key.

# 1. install, with the reference-player extra
uv sync --extra agents

# 2. configure: set OPENROUTER_API_KEY, optionally the models
cp .env.example .env

# 3. play one game; prints the game ID, writes data/exports/GAME_ID.json
uv run amaw run orison-crisis

# 4. re-export later from the SQLite database
uv run amaw export GAME_ID > game.json

# 5. resume a paused or interrupted game
uv run amaw run --resume-game GAME_ID

Before the first turn, amaw run seals an immutable run manifest. It records the models, prompt versions and hashes, scenario hashes, every game-loop condition, the guardrails and the code version. The server refuses to start an autonomous game without one. A resumed game inherits the sealed conditions and rejects any that differ.

Most settings can be given as a CLI flag or as an AMAW_* environment variable. A few are flag-only: --seed, --max-cycles and the per-role temperature, reasoning-effort and max-token flags. A game-loop condition resolves in this order: an explicit CLI flag, then an AMAW_* variable you actually set, then the scenario's default, then the released default. An unset variable never hides a scenario default.

08Changing parameters

Settings fall into two groups. Game-loop conditions change the game itself. Each one is a separate experimental treatment, and runs under different values must never be pooled. Harness and guardrail settings change how the agents operate and how much they can spend.

Game-loop conditions

Diplomacy length

--diplomacy-mode · AMAW_DIPLOMACY_MODE
open_diplomacyDiplomacy runs until every Actor is ready, or until timeout.
bounded_roundsStops after N complete rounds, set by --diplomacy-rounds-per-turn N. Cheaper and more predictable.

Who may Con

--con-mode · AMAW_CON_MODE
open_consEvery opponent may challenge every Argument.
sampled_sealedBefore any opponent acts, the server picks K challengers from a seeded rotation, set by --con-challengers-per-argument K. This is sampled opposition; don't report it as full Matrix opposition.

Con visibility

--con-reply-mode · AMAW_CON_REPLY_MODE
sealed_consOnly the Umpire reads Cons. The owner never sees them.
visible_replyCons and their authors are revealed to everyone, and the owner replies once with up to --reply-max-points (1–3) points. Requires umpire-v1.4 or later.

End-of-turn consequences

--consequence-mode · AMAW_CONSEQUENCE_MODE
noneThe turn ends straight after the last adjudication.
bounded_effects_v1A resolver model (the Umpire model unless --consequence-model names another) adds 0–3 public Effects. Each must cite this turn's adjudications or active public Effects. It is all or nothing, with no roll.

Umpire prompt

--umpire-prompt-version · AMAW_UMPIRE_PROMPT_VERSION
autov1.6 if the scenario declares rules, v1.4 under visible_reply, otherwise v1.3.
umpire-v1.3 … v1.7Every game defaults to v1.7: rules-aware, reply-aware, at most 3 Effects per branch, and a branch audit so the roll never decides another Actor's choice. Pin one version for every arm of a comparison. A rules scenario needs v1.5 or later; visible Cons need v1.4 or later. v1.3–v1.6 stay selectable to reproduce earlier runs.

Scenario-level settings

These live in scenario.yaml, not on the command line: max_turns, turn_order, primary_arguments_per_actor, max_cons_per_actor, rules, injects, starting Effects, Resources and their visibility. A scenario may also declare defaults for diplomacy_mode, con_mode and consequence_mode; an explicit flag or a set variable still overrides them. Changing any of them creates a new scenario version.

    10Benchmark method
    
  
    AMAW measures observable behaviour under stated conditions. It does not measure intelligence, aggression or trustworthiness. Suppose a run reports "Model X escalated in 72% of runs". That describes what Model X did in this scenario version, with this prompt, harness, Umpire and toolset. It is not a forecast that the real state it represents would escalate. benchmark-methodology §2
    

  
    The unit of measurement
    
  
    One game run combines one scenario version, one full Actor-to-model assignment, one seed, one player prompt version, one harness configuration and one fixed Umpire configuration. Every run gets its own game_id.
    

  
    Two kinds of benchmark
    
  
    
  
    
  
    
    
    
      
    Model benchmark: held constant
    
      
      
        
    • scenario version & Actors
    • player prompt
    • agent framework & tools
    • memory & context mode
    • Resource set
    • Umpire model, prompt & settings
    • consequence resolver
    • turn order & budgets
    • Con limits
    • inference profile
    • analysis code
      • 
      
    
    
    
    
    
      
    Varied
    
      
    • player model only
    
      
    An agent benchmark may vary the prompt, framework, memory or tools as well. Report its results as agent-configuration comparisons, not model comparisons.
    
    
    
  
    
  
    A model batch is checked against this whole list on every attempt. If anything drifts, it counts as an integrity failure: the batch stops, and the remaining attempts are recorded as not_run.
    

  
    Role rotation
    
  
    Some roles are easier to play than others, which would bias a comparison. With three models and three Actors, the acceptance design runs all 3! = 6 assignments. Each model plays each role, against each arrangement of opponents.
    
  
    
  
    Each bar has five segments, one per repetition. 6 assignments × 5 repetitions = 30 retained attempts. Failed games stay in the denominator and are never replaced.
    

  
    Seeds and scheduling
    

    seed = base_seed + assignment_index * 1000 + repetition_index
    
  
    Before the first game, the full schedule is generated and recorded, and the execution order is interleaved using a separate --scheduling-seed. Interleaving spreads provider load and model drift across all assignments instead of letting it pile up on one. The seed fixes the server's rolls only. It never makes LLM outputs identical.
    

  
    Playtest or analytical
    
  
    
    
    ClassWhenWhat you may report
    
    
      
    playtestDefault. Development, scenario tuning, smoke runs.Descriptive observations and telemetry only, however many runs there are.
    
      
    analyticalNeeds --analysis-plan PLAN, sealed before execution.Verified findings against the plan, with exploratory analyses clearly kept separate.
    
        
  
    
  
    The analysis plan (analysis-plan-v1) states the research question, hypotheses, treatment, fixed conditions, primary and secondary outcome measures, design, failure rules and assurance checks. It is identified by its sha256 hash. If you edit the plan after a run, that run becomes post_hoc_plan rather than predeclared. Check a set of runs with:
    

    uv run amaw analysis-plan verify plan.yaml games/*/export.json
    

  
    What you can and cannot claim
    
  
    
    
    Reasonable
      
      
    • "Model X used scenario Resources more often than Model Y under the same harness."
      • 
      
    • "Model Z completed more games across these runs."
      • 
      
    • "Role-balanced, under this fixed Umpire, Model X had a higher mean objective score."
      • 
    
    
    
    Overstated
      
      
    • "Country X would behave this way."
      • 
      
    • "Model X is more strategic in general."
      • 
      
    • "70% synthetic escalation means a 70% real risk."
      • 
      
    • "The Umpire's score is objective truth."

    11Reading results
    
  
    A single game produces one JSON export (format 16). A batch directory has this layout:
    

    runs/my-batch/
├── batch.json              # declared condition + sha256, schedule, every outcome, integrity
├── games/<attempt>/
│   ├── attempt.json        # identity + outcome of one scheduled attempt
│   └── export.json         # full admin export (partial if it failed)
├── games.csv               # one row per game: seed, hashes, completed, conditions
├── agents.csv              # per Actor: model requested/returned, tokens, cost, stalls
├── arguments.csv           # per Argument: probability, roll, success
├── messages.csv            # per Message: sender, public, recipients
└── resource_access.csv     # per search/read: who, what, results
    
  
    Some useful first checks on an export:
    

    jq '.game | {id, scenario_id, turn, phase, status, seed}' game.json
jq '.run_summary' game.json
jq '.effects[] | {description, active, visibility}' game.json
jq '.agent_runs[] | {role, actor_id, phase, completed, failure_reason}' game.json
    
  
    Failed attempts are kept with a category: agent_stall, provider_timeout, invalid_tool_loop, umpire_failure, server_failure or game_incompletion. The CSVs are a plain projection of the exports, and the exports remain the authority. AMAW computes no behavioural or psychological scores. Those belong to your analysis, and your plan must declare them.
    

    



    
  
    12Glossary
    
  
    
    
    Actor
    A party in the scenario (a state, agency or party), played by one LLM through one Seat.
    
    
    Seat
    The bearer token that identifies an Actor to the API.
    
    
    Argument
    An Actor's consequential move: action, desired effect and pros. The scenario gives each Actor 1–3 per turn.
    
    
    Con
    An opponent's reason why an Argument should fail or be narrowed.
    
    
    Effect
    An authoritative fact about the world. It can be public or private. It can be superseded but is never deleted.
    
    
    Resource
    A scenario document that agents can search and read, subject to visibility.
    
    
    Strategic memory
    One structured, private working state per Actor (commitments, offers, red lines, assessment, next intent). Each update replaces it. It persists across turns and changes nothing in the world.
    
    
    Umpire
    The LLM adjudicator. It proposes a mode, a probability and branch Effects, and never rolls.
    
    
    Consequence resolver
    An optional end-of-turn LLM pass that adds up to three evidence-linked public Effects.
    
    
    Run manifest
    The sealed, immutable record of every condition a game ran under.
    
    
    Condition
    A setting that changes the experiment. Runs under different conditions are never pooled.
    
    
    Assignment
    One mapping of models to Actor roles. Repetitions are counted per assignment.
